# Platform Compliance Detection Design

## Goal

Add a compliance checker that flags risky words and claims in generated ecommerce images before users export or publish them. The first release should focus on Chinese skincare and cosmetics images for Taobao/Tmall, JD, Douyin, Pinduoduo, and Xiaohongshu.

The checker is an assistant for review, not a legal guarantee. It should explain why a phrase is risky and suggest safer wording.

## Source Research

The stable rule base should be organized around laws, official regulatory guidance, and platform rules rather than scraped "forbidden word lists".

Primary sources:

- PRC Advertising Law: absolute terms such as "国家级", "最高级", and "最佳" are high risk in advertising.
- SAMR Advertising Absolute Terms Enforcement Guide, 2023: clarifies when absolute terms may or may not be treated as advertising violations.
  Source: https://www.samr.gov.cn/ggjgs/tzgg/art/2023/art_183b5cb48d9e4f0dba67f9f912a913ba.html
- SAMR guide interpretation: useful for implementation nuance and false positive handling.
  Source: https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/xwxcs/art/2023/art_c1ecaa66e3fa48beaed113e1627cd463.html
- Cosmetic Labeling Measures: cosmetics labels must not use medical terms, imply medical effects, or make false/exaggerated claims.
  Source: https://www.gov.cn/gongbao/content/2021/content_5631831.htm
- Douyin ecommerce rules on false advertising and advertising extreme terms: useful as a concrete platform example.
  Source: https://school.jinritemai.com/doudian/wap/article/110312

Platform-specific public word lists should be treated as supplemental examples. The app should keep the rule taxonomy stable and allow word entries to be updated without changing detection code.

## Risk Taxonomy

Each rule belongs to a category and severity:

- `block`: very likely to be rejected or illegal in ordinary ecommerce image copy.
- `warn`: risky unless the merchant has proof, authorization, or platform-specific qualification.
- `review`: context-sensitive, needs human confirmation.

Core categories:

- `absolute_claim`: 国家级, 最高级, 最佳, 第一, 顶级, 唯一, 首选, 全网最低, 销量冠军, 100%, 永久.
- `medical_claim`: 治疗, 治愈, 疗效, 消炎, 抗菌, 杀菌, 祛疤, 根治敏感, 修复皮炎.
- `cosmetic_claim`: 美白, 祛斑, 防晒, 防脱发, 祛痘, 修护, 抗皱, 紧致, 舒缓敏感. These are not always forbidden, but should be `review` or `warn` unless the product info includes supporting qualification.
- `authority_claim`: 国家认证, 央视推荐, 专家推荐, 医生推荐, 国家免检, 指定产品, 官方授权.
- `data_claim`: 临床证明, 实验室证明, 99%有效, 提升80%, 销量第一, 有效率.
- `promotion_claim`: 最低价, 史低, 亏本, 最后一天, 官方补贴, 平台补贴.
- `competitor_claim`: 秒杀同类, 吊打竞品, 比某品牌更好, 智商税.
- `platform_claim`: 官方旗舰, 自营, 专柜正品, 品牌授权, 保税直发. These require proof and should usually be `warn`.
- `sensitive_content`: political, pornographic, violent, gambling, superstition, discrimination, or illegal content.

## Detection Scope

The app currently generates most visible copy through server-side `text_layers`, then renders it onto the image. The compliance checker should inspect the text at several stages:

1. Product info review fields before image generation.
2. Promotion copy before campaign image generation.
3. Text layers generated by `language_renderer.py`.
4. Translated text layers for English, Thai, and Malay versions.
5. Edit instructions before image editing.
6. OCR text from final images as a later enhancement.

The first implementation should ship stages 1-5. OCR should be designed as an adapter but can be optional in the initial release.

## Architecture

Create a backend service:

- `backend/app/services/compliance_rules.py`
- `backend/app/services/compliance_checker.py`

Rule data should be stored as structured JSON or Python data in the first pass:

- rule id
- category
- severity
- platforms
- terms or regex patterns
- explanation
- safer suggestions
- qualification hints

Example result shape:

```json
{
  "source": "rules",
  "summary": {
    "status": "warn",
    "block_count": 1,
    "warn_count": 2,
    "review_count": 1
  },
  "issues": [
    {
      "id": "medical_claim_treat",
      "severity": "block",
      "category": "medical_claim",
      "platform_ids": ["tmall", "jd", "douyin", "pdd", "xiaohongshu_square", "xiaohongshu_portrait"],
      "term": "治愈",
      "matched_text": "7天治愈敏感",
      "location": {
        "source_type": "text_layer",
        "module_id": "main_effect",
        "field": "title"
      },
      "reason": "Cosmetic images should not imply medical treatment or cure.",
      "suggestion": "改为「舒缓不适肤感」或「帮助维持肌肤稳定」。"
    }
  ]
}
```

Add API endpoints:

- `POST /api/projects/compliance/check-text`: scan arbitrary fields, promotion copy, edit instructions, and generated text layers.
- `POST /api/projects/compliance/check-images`: future OCR wrapper that accepts image URLs and returns OCR-backed issues.

Generation can call the checker internally after layered text is created. It should not block image generation at first. Instead, generated image payloads should include `compliance` so the frontend can display the result.

## Frontend Experience

Add compliance state to image versions and project state:

- `ComplianceIssue`
- `ComplianceSummary`
- `ComplianceReport`

Recommended UI:

- Review step: add a compact "合规风险" panel next to AI extracted product info.
- Modules step: preflight campaign promotion copy before generation.
- Preview step: each image card shows a compliance badge: `通过`, `需确认`, `有风险`, or `高风险`.
- Image card issue drawer: show matched phrase, category, reason, and suggested replacement.
- Export actions: block download only for `block` issues if the user enables strict mode. Default first release should warn but not hard block, because false positives are expected.

Use short, action-oriented copy:

- "高风险：含医疗化表达"
- "需确认：功效词需要备案或资料依据"
- "建议替换：把「治愈」改为「舒缓」"

## False Positive Handling

The checker must avoid treating every occurrence as a violation.

Context rules:

- Product names and official ingredient names can be lower severity if they include risky characters but are not claims.
- Negative instructions such as "不要写治愈" should not be reported as final image copy.
- Cosmetic efficacy terms should become `review` when product info has matching authority material or effect claims.
- Absolute words inside non-advertising UI text should be ignored.

The service should return `ignored_matches` in debug/test mode to make rule tuning easier.

## OCR Adapter

Add an interface that can later use PaddleOCR, Tesseract, or a vision model:

```python
class OcrProvider(Protocol):
    async def extract_text(self, image_bytes: bytes) -> list[OcrTextBlock]:
        ...
```

Initial implementation can be a no-op provider. This preserves the API and lets the project add OCR without reshaping the frontend contract.

OCR is especially useful for:

- Product packaging text from uploaded images.
- Accidental model-generated text despite layered text mode.
- Edited images where the model may introduce new words.
- White background images that reuse packaging labels.

## Data Flow

Preflight flow:

1. Frontend sends product info, promotion info, and selected platform to `/compliance/check-text`.
2. Backend normalizes text, applies rules, and returns issues grouped by field.
3. Frontend shows issues in Review or Modules step.

Post-generation flow:

1. `_generate_module_image` creates or renders layered text.
2. Backend scans `text_layers` and default language version.
3. The image response includes `compliance`.
4. Frontend stores report in `GeneratedImageVersion`.
5. Export UI summarizes unresolved risks.

Translation flow:

1. `/render-language` translates text layers.
2. Backend scans translated layers with language-aware rules where available.
3. Language version response includes `compliance`.

## Testing Strategy

Backend unit tests:

- exact matches for absolute, medical, promotion, authority, and platform claims.
- regex matches for percent/data claims.
- context suppression for negative instructions.
- severity downgrade for cosmetic efficacy terms with supporting evidence.
- platform filtering.

API contract tests:

- `check-text` returns stable summary and issue fields.
- generation response includes `compliance` when layered text exists.
- render-language response includes language compliance report.

Frontend tests:

- type coverage for compliance reports in generated image versions.
- preview card renders the correct badge by summary status.
- export area shows warnings when selected images contain issues.

Manual test cases:

- "7天治愈敏感肌" should be `block`.
- "全网最低价" should be `block` or `warn` depending platform and strictness.
- "美白淡斑" should be `review` unless product info has qualification evidence.
- "不要写治愈" should not be reported as final copy.
- "舒缓干燥泛红" should pass or remain low-risk.

## Open Decisions

- Whether first release should hard-block export on `block` issues or only warn.
- Whether users need a rule-management UI, or whether rules can remain code-managed initially.
- Which OCR provider to use after the text-layer scanner lands.
- Whether to support platform-specific override files for merchant teams.

Recommended defaults:

- First release warns but does not block export.
- Rules are code-managed with structured data.
- OCR adapter ships as no-op, real OCR comes next.
- Include platform IDs on every issue even if most initial rules are global.
